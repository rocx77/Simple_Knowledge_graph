You are implementing a complete end-to-end **Knowledge Graph MVP / Proof of Concept** in Python.

The purpose of this project is a case-study demonstration, not a production system. The final result must demonstrate the full pipeline:

DOCUMENTS
→ NLP preprocessing
→ entity extraction
→ POS/dependency analysis
→ coreference resolution
→ relation extraction
→ triple generation
→ knowledge graph construction
→ interactive graph visualization
→ simple natural-language query parsing
→ graph traversal
→ human-readable answers + supporting evidence

The system must work entirely locally and must not depend on external LLM APIs, cloud services, or internet access at runtime.

The implementation should prioritize:

1. Reliability on the provided corpus.
2. Explainability.
3. Clean modular architecture.
4. A visually impressive graph UI.
5. Easy demonstration during a case study.
6. No unnecessary over-engineering.

Do not ask for architectural clarification. Make the implementation according to the specification below.

# 1. TECH STACK

Use Python.

Required libraries:

* spaCy
* fastcoref
* PyTorch
* NetworkX
* PyVis
* Streamlit
* pandas

Recommended spaCy English model:

* `en_core_web_sm`

Use spaCy for:

* tokenization
* sentence segmentation
* POS tagging
* dependency parsing
* NER
* noun chunks

Use a spaCy `EntityRuler` or equivalent rule layer to supplement NER because some entities in the provided fictional corpus will not necessarily be recognized reliably by the generic NER model.

Use:

```python
from fastcoref import FCoref
```

for coreference resolution.

The coreference model should automatically select:

```text
cuda:0
```

when CUDA is available, otherwise:

```text
cpu
```

Do not hard-code GPU-only execution.

Use logic equivalent to:

```python
device = "cuda:0" if torch.cuda.is_available() else "cpu"
model = FCoref(device=device)
```

Make the device configurable through an environment variable if convenient:

```text
COREF_DEVICE
```

with automatic fallback to CPU.

Do NOT introduce Neo4j, Redis, Elasticsearch, Kafka, Docker, LangChain, vector databases, or an LLM for this MVP.

The graph will live in memory as a NetworkX graph and will also be serialized to JSON for persistence.

# 7. ENTITY RECOGNITION STRATEGY

Use a hybrid approach.

Primary source:

```text
spaCy NER
```

Secondary correction/enrichment:

```text
spaCy EntityRuler
```

Create deterministic patterns for the known demonstration entities.

This is intentional.

The purpose of the case study is to demonstrate an NLP pipeline rather than gamble on whether a generic NER model recognizes every fictional company/product name.

Entity normalization must map mentions to one canonical entity.

For example:

```text
"OrionEdge"
"the platform"
```

should eventually map to:

```text
ORIONEDGE
```

Do not make separate nodes for these mentions.

---

# 8. STAGE 3 — COREFERENCE RESOLUTION

Run FastCoref over each document.

Example:

```python
coref_model.predict(texts=[text])
```

Use:

```python
preds[0].get_clusters(as_strings=False)
```

and:

```python
preds[0].get_clusters()
```

to obtain clusters.

Create a mapping:

```text
mention span → canonical entity
```

Use the first strong named mention in a cluster as the preferred canonical entity.

For example, conceptually:

```text
"Aether Analytics"
        ↓
"the company"
```

should become:

```text
Aether Analytics
```

and:

```text
"Nila Rao"
      ↓
    "She"
```

should become:

```text
Nila Rao
```

Coreference must happen BEFORE final relation normalization.

The system should retain both:

```text
original mention
resolved entity
```

for explainability.

Example:

```python
{
    "mention": "the bank",
    "resolved_to": "Helios Bank",
    "source": "fastcoref"
}
```

# 11. REQUIRED RELATION RULES

Implement explicit extraction patterns for the following grammatical forms.

### founded

Example:

```text
Aether Analytics was founded by Dr. Mira Sen.
```

Create:

```text
Dr. Mira Sen
   --founded-->
Aether Analytics
```

Canonical relation:

```text
founded
```

---

### develops

Example:

```text
The company develops OrionEdge.
```

After coreference:

```text
Aether Analytics develops OrionEdge.
```

Triple:

```text
(Aether Analytics, develops, OrionEdge)
```

---

### leads

Example:

```text
Mira Sen leads Project Aurora.
```

Triple:

```text
(Dr. Mira Sen, leads, Project Aurora)
```

Example:

```text
Nila Rao ... leading Project Aurora.
```

Triple:

```text
(Nila Rao, leads, Project Aurora)
```

---

### focuses_on

Example:

```text
The project focuses on graph-based transaction analysis.
```

Create:

```text
(Project Aurora, focuses_on, graph-based transaction analysis)
```

Since the object may not be a canonical named entity, allow literal/attribute nodes.

---

### works_at

Example:

```text
Arun Mehta joined Aether Analytics.
```

Normalize the semantic relation to:

```text
(Arun Mehta, works_at, Aether Analytics)
```

This is acceptable because the graph is representing the current employment relationship for the case study.

---

### works_on

Example:

```text
He works on OrionEdge.
```

After resolution:

```text
(Arun Mehta, works_on, OrionEdge)
```

---

### collaborates_with

Example:

```text
The engineer collaborates with Nila Rao.
```

Resolve:

```text
the engineer → Arun Mehta
```

Triple:

```text
(Arun Mehta, collaborates_with, Nila Rao)
```

Treat this relation as bidirectional for query purposes, while keeping one canonical stored direction.

---

### partners_with

Example:

```text
Aether Analytics partnered with Quantum Forge.
```

Triple:

```text
(Aether Analytics, partners_with, Quantum Forge)
```

For query purposes this relation is symmetric.

---

### deployed_at

Example:

```text
OrionEdge was deployed at Helios Bank.
```

Triple:

```text
(OrionEdge, deployed_at, Helios Bank)
```

---

### uses

Example:

```text
The bank uses the platform.
```

Resolve:

```text
the bank → Helios Bank
the platform → OrionEdge
```

Triple:

```text
(Helios Bank, uses, OrionEdge)
```

---

### improves

Example:

```text
Nila Rao improved the Entity Resolution Engine.
```

Triple:

```text
(Nila Rao, improves, Entity Resolution Engine)
```

---

### integrated_into

Example:

```text
Aether Analytics plans to integrate Aurora into OrionEdge.
```

The semantic graph relation should be:

```text
(Project Aurora, integrated_into, OrionEdge)
```

The company remains the source/evidence context.

Do not incorrectly create:

```text
(Aether Analytics, integrates, Aurora)
```

as the main representation.

---

### customer_of

From:

```text
Helios Bank renewed its contract with Aether Analytics.
```

create:

```text
(Helios Bank, customer_of, Aether Analytics)
```

This is a semantic inference from the provided sentence and should be marked as:

```text
inferred=True
```

or have lower rule confidence than a directly stated relation.

Do NOT pretend inferred relations are literally stated if they are not.

# 12. TRIPLE DATA MODEL

Every extracted triple must contain provenance.

Use a structure equivalent to:

```python
{
    "subject": "Arun Mehta",
    "subject_id": "person:arun_mehta",

    "relation": "works_on",

    "object": "OrionEdge",
    "object_id": "product:orionedge",

    "document_id": "doc_02_team",
    "sentence": "He works on OrionEdge.",

    "original_subject": "He",
    "original_object": "OrionEdge",

    "coref_resolved": True,

    "inferred": False,

    "confidence": 0.90
}
```

The confidence value is NOT a probability.

It should be described in the UI as:

```text
Extraction confidence
```

and represent deterministic rule confidence.

Suggested values:

```text
1.00 = direct named-entity relation
0.90 = relation involving successfully resolved coreference
0.80 = deterministic semantic inference
```

These values are heuristic labels, not statistical probabilities.

# 37. NO HIDDEN MAGIC

Avoid opaque shortcuts.

Do not do something like:

```python
if query == "Who founded Aether Analytics?":

```

The query engine must actually:

```text
parse query
→ identify entity
→ identify relation
→ determine direction
→ query graph
→ return result
```

The known entity dictionary and deterministic relation patterns are allowed because this is an MVP.
